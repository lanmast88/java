# Страховая компания — консольная информационная система

Курсовая работа по программированию корпоративных систем (РТУ МИРЭА).
Java 25 + PostgreSQL через JDBC (без ORM), сборка Maven, экспорт в Excel на Apache POI.

Предметная область: страхователь (`Client`), полис (`Policy`) и страховой случай (`Claim`).
Полис — основная сущность: по нему сделан полный CRUD, поиск, фильтры, сортировки и статистика.

## Как запустить

```bash
# 1. База и схема (один раз)
createdb -U postgres insurance
psql -U postgres -d insurance -f db/schema.sql
psql -U postgres -d insurance -f db/data.sql     # 5 клиентов, 8 полисов, 6 убытков

# 2. Параметры подключения
cp .env.example .env                              # DB_URL / DB_USER / DB_PASSWORD

# 3. Сборка и запуск
mvn clean compile
mvn spring-boot:run
```

`db/data.sql` начинается с `TRUNCATE ... RESTART IDENTITY CASCADE`, поэтому его можно
перезапускать сколько угодно — демонстрационные данные вернутся в исходное состояние.

## Архитектура

```
Console UI → Service → Repository (JDBC) → PostgreSQL
```

| Пакет        | Чем занимается                                                        |
|--------------|-----------------------------------------------------------------------|
| `model`      | Данные и их инварианты: проверки в конструкторах и сеттерах, `enum` с поведением |
| `repository` | Только SQL и маппинг `ResultSet` → объект, ничего не печатает          |
| `service`    | Бизнес-правила, расчёт премии, переходы статусов, статистика           |
| `ui`         | Меню, чтение ввода, форматирование вывода; не знает ни про SQL, ни про `Connection` |
| `exception`  | Три своих исключения-наследника `RuntimeException`                     |
| `util`       | `DatabaseManager` (пул соединений), `ExcelExporter`, `Formats`          |

Проверить разделение слоёв просто: `grep -r "SELECT" src/main/java/ru/mirea/insurance/ui`
и `grep -r "System.out" src/main/java/ru/mirea/insurance/repository` не находят ничего.

Сборка объектов — в Spring-контексте, `Main` только поднимает контекст, а `StartupRunner`
передаёт собранный `ConsoleApp` в работу: репозитории → сервисы → меню → `consoleApp.run()`.

## Меню

```
СТРАХОВАЯ КОМПАНИЯ
 1. Клиенты           добавить · список · по ID · поиск по ФИО · изменить · удалить
 2. Полисы            оформить · список · по ID · поиск по номеру · полисы клиента ·
                      изменить условия · удалить · фильтр по виду · фильтр по статусу ·
                      сортировка по дате окончания · сортировка по страховой сумме ·
                      ввести в действие · расторгнуть · отметить истёкшим
 3. Страховые случаи  заявить · по полису · все · по ID · одобрить · отклонить · выплатить
 4. Статистика        6 показателей на Stream API + гистограмма по видам страхования
 5. Экспорт в Excel   лист «Полисы» в policies.xlsx
 6. Таблицы БД        список таблиц из information_schema и содержимое выбранной
 7. Демонстрация бизнес-правил
 0. Выход
```

Любое исключение перехватывается в `Menu.show()` вокруг всего блока обработки пункта,
поэтому после ошибки программа печатает сообщение и снова показывает меню.

## Пять бизнес-правил и их формулировки

Пункт меню 7 прогоняет пять заведомо неверных вызовов подряд (`RulesDemoService`).
Ничего не записывается в базу, после каждого сообщения программа продолжает работать —
это и есть сценарий демонстрации на защите:

| № | Правило | Сообщение системы |
|---|---------|-------------------|
| 1 | Полис нельзя оформить на несуществующего клиента | `Полис не оформлен: клиента с id=999999 нет в базе` |
| 2 | Страховая сумма положительна, период корректен | `Дата начала должна быть раньше даты окончания` / `Страховая сумма должна быть больше нуля` |
| 3 | У клиента не больше одного действующего полиса одного типа | `У клиента Соколов Артём уже есть действующий полис ОСАГО — OSAGO-2026-0001` |
| 4 | Убыток — только по действующему полису и только за дату внутри его периода | `Дата события 19.02.2026 вне периода действия полиса OSAGO-2026-0001 (01.03.2026 – 01.03.2027)` |
| 5 | Выплата не больше страховой суммы за вычетом франшизы и только по одобренному убытку | `Выплата 2 000 000,00 ₽ превышает лимит по полису KASKO-2026-0009: страховая сумма 800 000,00 ₽ минус франшиза 8 000,00 ₽ = 792 000,00 ₽` |

Дополнительно к пятёрке:

* клиента с действующими полисами удалять нельзя — `Клиента Проверкин Тест нельзя удалить:
  действующих полисов — 1 (KASKO-2026-0009). Сначала расторгните договоры`;
* запрещённый переход статуса отклоняется — `Полис KASKO-2026-0009: переход «расторгнут» →
  «расторгнут» запрещён, так можно только из «черновик или действует»`;
* выплата по отклонённому убытку отклоняется — `Убыток #3: переход «отклонён» → «выплачен»
  запрещён, так можно только из «одобрен»`.

Премия никогда не вводится руками: `PolicyType.calculatePremium()` умножает страховую
сумму на тариф вида страхования (ОСАГО 0.05, КАСКО 0.08, ДМС 0.03, имущество 0.02).
Там же лежит доля безусловной франшизы, из неё считается лимит выплаты для правила 5.

## Жизненный цикл статусов

```
Полис:  DRAFT → ACTIVE → EXPIRED
                      ↘ CANCELLED          обратных переходов нет
Убыток: SUBMITTED → APPROVED → PAID
                 ↘ REJECTED               REJECTED → PAID запрещён
```

## Некорректный ввод

Весь ввод идёт через `ConsoleReader`: строка читается `nextLine()`, разбирается в
`try/catch` и при ошибке запрос повторяется.

| Метод | Что проверяет | Пример сообщения |
|-------|---------------|------------------|
| `readMenu` / `readChoice` | номер пункта в диапазоне | `нет такого пункта меню, введите число от 0 до 7` |
| `readId` | целое число | `ID должен быть целым числом` |
| `readRequired` | непустая строка | `фамилия страхователя обязательна` |
| `readDate` | формат и существование даты | `неверный формат даты «1.5.26», нужно ДД.ММ.ГГГГ, например 01.10.2026` · `даты 32.13.2026 не существует` |
| `readMoney` | число и положительность | `неверное число «abc», пример: 800000 или 800000,50` |
| `readEnum` | выбор значения enum номером из списка | `введите число от 1 до 4` |
| `confirm` | да/нет | `ответьте «да» или «нет»` |

## Требования задания → где это в коде

| Требование | Реализация |
|------------|------------|
| Интерактивное меню, не завершается после одной операции | `ui/Menu.show()` — цикл `while (running)`, пункт 0 — выход |
| Две связанные сущности + участник предметной области | `Client` ← `Policy` по `client_id`, третья — `Claim` |
| Полный CRUD по основной сущности + поиск, фильтрация, сортировка | подменю «Полисы», `PolicyService` |
| Минимум один enum | `PolicyType` (с тарифом и франшизой), `PolicyStatus`, `ClaimStatus` |
| Минимум 5 бизнес-правил в коде | `PolicyService` (1–3), `ClaimService` (4–5), плюс правило удаления в `ClientService` |
| Обработка некорректного ввода без падения | `ConsoleReader` + перехват исключений в `Menu.show()` |
| 2 способа поиска, 2 фильтра, 2 сортировки | поиск по ФИО (`ILIKE ?`) и по номеру полиса; фильтры по виду и статусу; сортировки по дате окончания и страховой сумме (`Comparator.comparing`) |
| Статистика, минимум 5 показателей | `StatisticsService` — 6 показателей на Stream API (`reduce`, `groupingBy`, `counting`) |
| Экспорт в Excel `.xlsx` | `util/ExcelExporter` на Apache POI, `ExportService` |
| ООП: инкапсуляция, интерфейс, полиморфизм, коллекции, свои исключения | private-поля и проверки в моделях; интерфейсы `CrudRepository<T>` и `ConnectionSource`; абстрактный `Menu` и его четыре реализации; `List`/`Map`/`Optional`; три своих исключения |
| Запрет «вся система в Main» | пакеты `model`, `repository`, `service`, `ui`, `exception`, `util`; в `Main` 12 строк — только запуск контекста |
| SQL не в коде меню | SQL только в `repository/*`, меню работает через сервисы |
| Пункт «Вывести таблицы базы данных» | `SchemaRepository` (`information_schema.tables` + `ResultSetMetaData`) → `DatabaseService` → пункт 6 |

## Сценарий демонстрации

Сквозной путь, который проходит через все слои и все требования:

1. **Клиенты → Добавить** — заводим страхователя (пустое ФИО не принимается).
2. **Полисы → Оформить** — выбираем вид страхования номером, вводим страховую сумму;
   премия считается по тарифу сама и совпадает с `страховая сумма × тариф`.
3. **Страховые случаи → Заявить убыток** — дата события внутри периода действия полиса.
4. **Одобрить**, затем **Выплатить** — путь `SUBMITTED → APPROVED → PAID`;
   попытка выплатить больше лимита отклоняется.
5. **Полисы → Расторгнуть** — повторное расторжение отклоняется как запрещённый переход.
6. **Клиенты → Удалить** — пока есть действующий полис, удаление отклоняется;
   после расторжения клиент удаляется вместе с закрытыми полисами.
7. **Статистика** — шесть показателей и гистограмма по видам страхования.
8. **Экспорт полисов в Excel** — появляется `policies.xlsx` с заголовками и данными.
9. **Вывести таблицы базы данных** — выбор таблицы номером и её содержимое.
10. **Демонстрация бизнес-правил** — пять неверных вызовов подряд, пять разных сообщений,
    программа продолжает работать.

Демонстрационные данные: 5 клиентов, 8 полисов (5 действующих, по одному черновику,
истёкшему и расторгнутому), 6 убытков во всех четырёх статусах — этого хватает,
чтобы показать фильтры, сортировки и все переходы статусов без подготовки.
